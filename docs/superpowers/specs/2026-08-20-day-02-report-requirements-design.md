# 第 2 天报告定向精修设计

## 目标

只修改 `docs/reports/day-02.md`，严格符合教师新发布的第 2 天日报结构与评分标准，不改动其余八篇报告、代码或项目行为。

## 固定结构

正文依次使用以下七个二级标题，不合并、不改名：

1. 基本信息
2. 今日目标
3. 组成部分
4. 与需求的对应
5. 技术选型
6. 今日完成与自检
7. 问题、计划与 AI 沟通

## 内容设计

- 基本信息写明课题和“本人独立完成”，不推测真实姓名。
- 今日目标限定为系统组成、需求映射和技术选型，不把后续实现写成今日目标。
- 组成部分使用表格，列出名称、职责、输入、输出或上下游、负责人。组件包括 Web、HTTP API、Job Service、JSON Store、FIFO/Worker、Renderer、Printer Adapter 和交付材料。
- 与需求的对应逐项覆盖 Day 1 的两类业务打印、任务队列、状态与失败重试、本地接口与页面、双平台边界、可复现交付。每项给出承担组件、接口或数据流，以及后续验收依据。
- 技术选型至少比较两个可行方案。服务比较自研 Go、页面直接命令和 C-Lodop；渲染比较 HTML + Chroma + Chromedp 与纯 Go PDF；打印比较统一 PDF Adapter 与各业务直接调用平台命令。每组写明入选与放弃理由。
- 今日完成与自检只写已经确定的架构、边界、状态机和选型；HTTP 页面、真实 PDF、平台 runtime 等仍标为后续实现或验证。
- AI 沟通分别写一个不成功和一个有效案例，说明提问约束如何影响输出质量，不虚构逐字回答。
- 明日安排落到任务字段、状态机、错误码和 Store/Worker 接口约定。

## 表达与事实约束

- 正文控制在教师建议的 800～2000 个中文字符附近。
- 不粘贴大段代码、完整 JSON、测试输出或提交哈希。
- 不写仓库地址、录屏外链、密钥或账号信息。
- 保持既有事实：仅监听回环地址、候选端口 17653-17660、容量 100、五状态、Windows SumatraPDF、Linux CUPS、默认 Fake Printer。
- 不把方案确定写成平台实测，不把交叉编译或 Fake 写成真实打印。

## 完成标准

1. 七个标题与教师模板完全一致且顺序正确。
2. 组成表包含职责、输入输出/上下游和负责人。
3. Day 1 六项必做都有明确承担组件，无无人承担项。
4. 至少三组技术比较均有入选理由和放弃理由。
5. 同时包含不成功和有效的 AI 沟通实例。
6. 正文长度处于建议范围，无仓库地址、外链、密钥和占位符。
7. `go test ./docs -count=1` 与 `git diff --check` 通过。
