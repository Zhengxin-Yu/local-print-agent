## 使用场景与主路径

程序设计竞赛现场需要打印两类材料：队伍通过题目后，工作人员打印气球小票用于分发气球；参赛队需要纸面检查时，打印带行号和语法高亮的源代码。浏览器不能安全、统一地直接控制本地打印机，因此在打印工作站运行一个仅监听回环地址的 Go 服务，由 Web 页面提交结构化任务。

主路径确定为：

```text
浏览器提交任务 -> 本地 HTTP API 受理 -> FIFO 队列 -> HTML 模板 -> PDF
-> 系统打印适配器 -> 状态回传 -> Web 查询或重试
```

状态统一为 `queued -> rendering -> printing -> succeeded`，渲染或打印失败时进入 `failed`。其中 `succeeded` 只表示当前适配器接受调用；平台命令成功和物理出纸还需分别取证，不能混为同一验收结论。

## 九天范围

### 必做

1. 气球小票：接收比赛、队伍、房间、题号、颜色和通过时间，生成窄纸 PDF。
2. 源代码打印：接收语言与源码，生成带高亮、行号、自动换行、页眉和页码的 A4 PDF。
3. 任务管理：提供容量受控的 FIFO、五状态流转、失败原因和失败任务重试。
4. 本地接口与页面：提供探活、打印机列表、创建/列表/详情/预览/重试接口及 Mock Web。
5. 双平台边界：Windows 使用 SumatraPDF，Linux 使用 CUPS；缺少平台环境时仍能用明确标识的 Fake Printer 演示非实体主路径。
6. 可复现交付：README、Windows/Linux 启动脚本、测试说明、API 文档、演示脚本和录屏计划。

### 不做

- 不做完整 OJ、判题、榜单或未确认的 CCPCOJ 接口对接。
- 不做账号权限、远程访问、云打印、浏览器插件或桌面 GUI。
- 不自研打印机驱动，不集成 Lodop/C-Lodop，不实现多打印机负载均衡。
- 不承诺操作系统打印的 exactly-once；进程崩溃窗口可能导致人工重试后重复提交。
- 不把 Fake Printer、PDF 预览、命令参数测试或交叉编译当成真实系统队列和物理出纸证据。

以上边界把工作集中在一条九天内可验证的完整链路，避免扩展到 OJ、权限系统和硬件驱动后失去交付重点。

## 风险、处理与 AI 沟通

| 风险 | 当前处理 |
| --- | --- |
| Chrome 路径和版本因机器而异 | 集中配置浏览器路径，启动时返回稳定且可诊断的渲染错误。 |
| Windows 与 Linux 打印工具不同 | 统一输出 PDF，只在小型 Adapter 中隔离 SumatraPDF/CUPS 差异。 |
| 中文字体或分页异常 | 验收样例强制包含中文队名、中文注释、长行和多页源码。 |
| 端口占用 | 在固定候选段逐个监听，并保持只绑定 `127.0.0.1`。 |
| 环境不足导致证据被高估 | 将 Fake、受控命令、交叉编译、系统队列和物理出纸分层记录。 |

本日使用 AI 辅助检查范围时，最有效的约束是同时提供“必做、不做、九天周期和验收证据层级”，而不是只要求补充风险。这样输出能够围绕主路径收敛，也避免把“命令返回成功”误写成“已经出纸”。范围和技术结论均由本人结合课程要求复核。
